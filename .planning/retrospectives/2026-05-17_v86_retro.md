## What worked

1. **Reading the mandate-wording shift as a strong signal.**
   V80 through V85 used identical mandate wording ×5 times. V86 changed "AI CFD demo展示" to "全流程CFD能力". The temptation was to treat this as noise and continue the V81/V84-mirror substantiation pattern. Instead I noted the deliberate wording change in the charter §1 preamble, asked the user one focused question with 3 interpretations (V6 substantiation / V7 live-trigger / V7 mesh-capability), and let the user redirect. **Lesson**: when a user changes wording after N verbatim re-issues, the change carries information. Use AskUserQuestion to surface the interpretation choice — a single 30-second prompt prevents a multi-week mis-pivot.

2. **Pre-implementation surface scan (DEC-V61-088) caught a major scope mistake before commit.**
   The user-selected preview for V7 Live Solver Trigger assumed "V86.2 backend POST /api/cases/{id}/runs route (+ auth · + idempotency · + audit-trail)". Surface scan with `grep -rn "^@router.post" ui/backend/routes/` immediately found `POST /api/import/{case_id}/solve-stream` already implementing the desired behavior. I STOPPED before charter commit and surfaced via a second focused AskUserQuestion (disposition: extend / parallel-new / refactor). User selected (a) extend. **Lesson**: DEC-V61-088 saved this arc from a multi-week mis-pivot. The discipline pays off every time the mandate or user-selected design implies new backend work — the scan is 5 minutes; the savings are weeks.

3. **Two-question gate (mandate-interpretation + disposition) felt friction-free.**
   Past V80-V85 arcs had zero AskUserQuestion calls — I just interpreted and executed. V86 had 2. Total latency cost: ~1 minute of user input. Total value: prevented a wrong-axis pivot (Q1) + prevented endpoint duplication (Q2). **Lesson**: AskUserQuestion is the right tool when (a) mandate wording changes signal a new axis OR (b) surface scan discovers substantial pre-existing implementation. Use it sparingly but unambiguously when those conditions hit.

4. **Legacy SolveStreamContext provided the right pattern but not the right shape.**
   `step_panel_shell/SolveStreamContext.tsx` had a battle-tested SSE-parsing implementation with AbortController + generation counter + 4-state machine. I copied the approach but cast it as a hook (`useSolverRunStateV7`) instead of a Context provider, matching v3's hook-first idioms. Zero contract test failure on first run. **Lesson**: legacy patterns are starting points, not final blueprints. Adapt to the host substrate's idioms (Context → hook here) while preserving the race-condition handling.

5. **V7 contract decomposition fell out cleanly at 4 pieces.**
   - V7.A: pure presentational button (no state)
   - V7.B: pure state machine hook (no UI)
   - V7.C: pill component + state machine callback extension
   - V7.D: post-run handoff hook (no UI · just side-effect orchestration)
   This separation made unit tests trivially focused. Each sub-DEC averaged 110-250 LOC, each test file 8-17 tests. **Lesson**: when a feature naturally decomposes into "presentation + state machine + side effects", build them as 3 layers (component / hook / hook) with clear contracts at each boundary. Avoid the monolithic-Context anti-pattern from the legacy code.

6. **V130 invariant enforced at THREE layers**:
   - Lexical (denylist test in V7.A button text)
   - Structural (V7.B `fetchImpl=vi.fn()` mount-time zero-call assertion)
   - Architectural (V7.A is pure presentational · cannot fire mutations without a parent click event)
   No future "AI runs solver" regression can slip past all three. **Lesson**: V130-class invariants deserve defense-in-depth · combine prose denylists + mount-time assertions + architectural impossibility.

7. **iter-0 = 100/100 immediately (V83/V85 pattern reproduced).**
   V86 substrate is all steady-state UI (no post-click async-mount baselines added). V84's iter-0 = 86 drift was a one-off; V85 + V86 both clean. **Lesson**: design new visual surfaces as steady-state-determined-by-URL+props, not post-click-async-mounted. The V84.6 lesson generalized correctly.

## What surprised us

1. **The user's preview for the V7 axis ASSUMED new backend endpoints existed.**
   The preview I built for the AskUserQuestion explicitly listed "V86.2 backend POST /api/cases/{id}/runs route (+ auth · + idempotency · + audit-trail)". When I ran the surface scan, the existing endpoint was already there — and already counted in V132=9. The user's preview was based on my pre-scan estimate; surface scan disproved the assumption. **Lesson**: previews in AskUserQuestion are estimates, not commitments. When the actual implementation is different (cheaper / different shape), surface that BEFORE committing to the charter via a second focused question. The 2-question pattern (interpret → discover → re-decide) is sometimes correct.

2. **The Engineer Control Rail referenced in the charter doesn't exist as a named component.**
   V86 charter §3 / V7 blueprint §2 refer to V7.A surfacing in "Engineer Control Rail". When I went to mount the button in V86 scope, I discovered there's no `EngineerControlRailV3.tsx` component — the rail is conceptual (BottomPanelV3 + RightPanelV3 collectively serve as engineer-mode controls in the current v3 layout). I deferred actual mounting to V87 rather than inventing a new container component just-in-time. **Lesson**: when a charter references a substrate name (e.g., "Engineer Control Rail") that doesn't have a direct file mapping, validate during surface scan whether the name is conceptual or literal. Defer mounting until the substantiation arc; keep V86 scoped to building the V7 contracts as orthogonal pieces.

3. **`useSearchParams` test harness footgun**: `??` treats `null` as nullish.
   In `RunSolverButtonV7.contract.test.tsx`, my harness defaulted `caseId` via `props.caseId ?? "lid_driven_cavity"`. Test passed `caseId: null` explicitly → harness silently defaulted to "lid_driven_cavity" → test failed. Fix: `"caseId" in props ? props.caseId! : "lid_driven_cavity"`. **Lesson**: test harnesses that allow explicit-null overrides must distinguish "not provided" from "explicit null" — the `in` operator or sentinel pattern is required. The `??` operator is wrong here.

4. **Audit-package downloads schema had snake_case fields, not the camelCase I assumed.**
   `AuditPackageDownloadUrls` uses `manifest_json` / `bundle_zip` / `bundle_html` / `bundle_pdf` / `bundle_sig` — not `manifest` / `signature` as I initially wrote. Caught by tsc post-V86.5. **Lesson**: when consuming an existing type, READ the actual definition before assuming field names. 5-second `grep` saves a typecheck round.

5. **`useReducer` vs `useState` decision was easier than expected.**
   V7.B has 6 states with constrained transitions (idle → starting → running → done/failed/cancelled → idle). Used `useReducer` for the explicit state machine; tests verify all transitions. Alternative would have been 4 separate `useState` calls (state · runId · startedAt · endedAt) with imperative setters everywhere — harder to verify atomic transitions. **Lesson**: when a hook has constrained state transitions (not just unrelated mutable values), `useReducer` is the right primitive. The explicit action type list is documentation.

## What I'd do differently

- **Should have done the surface scan BEFORE writing the user-question preview.** I built the AskUserQuestion preview for V7.A with "V86.2 backend POST /api/cases/{id}/runs route" assumed. If I'd run the surface scan first, the preview would have been accurate ("V86.2 frontend wiring · backend already exists"). The user would have selected the same axis but the disposition Q2 would have been redundant. Net: 1 turn cost for the 2-question gate. Not a huge issue but worth flagging.
- **Could have committed RunSolverButtonV7 mount to V86 scope** if I'd done a quick check for an existing Engineer-Control-Rail container. Instead I deferred to V87. This is conservative — the cost is one extra arc — but it also kept V86 scope tight. Trade-off.
- **Test harness `??` bug cost ~2 minutes.** Trivial fix but a fully-typed harness pattern (use `??` + nullable defaults) would have caught it. Could codify in a shared test-harness lib.
