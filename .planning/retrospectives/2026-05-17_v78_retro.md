## What worked

1. **Saying "no new pillar" was the right call**.
   V67-C → V77 added 9 pillars across 9 arcs — every arc grew the framework. V78 broke that. The pillar-add reflex was producing easy wins (the new axis starts at 0, work moves it to 100). V78 forced harder work because old subscores got rebalanced down (25→20) AND new substantive subscores (audit_package_e2e, backend_sse_e2e, ssim_tool_present) had to actually pass. Same "100/100" score, harder to achieve.

2. **Backend SSE was 2 hours, same as V77 frontend was**.
   The "V71.L 8-arc-aged bookmark" turned out to be backend-side simpler than the frontend hook itself was. FastAPI's `StreamingResponse` + an async generator + `await request.is_disconnected()` is ~150 LOC. **Lesson**: when a bookmark says "X is missing", check if X is conceptually small but psychologically large.

3. **SSIM tool implementation without scikit-image**.
   numpy + PIL only · cumulative-sum trick for O(N) uniform filter · 60 LOC for the core SSIM math. Self-pair returns 1.0; different baselines return 0.6. The 5-retro carry was waiting on "scikit-image not installed" — but the dependency wasn't actually needed.

4. **Real WCAG violation surfaced AND fixed in one iter**.
   V77 SolverInflightTicker had `overflow: auto` without `tabIndex` — a scrollable-region-focusable serious-impact axe rule. V78's UX 100%-specs threshold tightening was what surfaced it. `tabIndex={0}` + `role="log"` + `aria-live="polite"` fix. **Lesson**: tightening scorers catches real defects, not just hardens scoring.

## What surprised us

1. **V77's "100/100 close" was hiding 3 baseline regressions waiting to happen**.
   sse-stream-status pill captured under V77 (backend = 404 → "offline") looked one way. V78.1 made backend live, status flipped to "open"/"connecting" → 3 baselines drifted at iter-0. This is the SAME kind of fragility V77 retro called out: V73.1 whitelist change time-bombed 2 V72 specs. The pattern repeats: **frontend changes that depend on backend response state are time bombs across arcs**. The SSIM tool would have flagged this as structural drift, not just pixel drift.

2. **Pillar 13/16 rebalance was harder than expected**.
   Re-weighting 4×25 → 5×20 means every existing subscore loses 5 points if it was at 25. If one of the new subscores fails, total drops to 80 (not 100). This is the right pain — V78 work HAD to actually pass, not just exist. But it also means future arcs can't "add a subscore" without thinking about the rebalance math.

3. **`uv run pytest` PYTHONPATH must be set explicitly**.
   First run: `uv run pytest ui/backend/tests/test_solver_stream.py` → `ModuleNotFoundError: No module named 'ui'`. Fix: `PYTHONPATH=. uv run pytest ...`. Future scorers should set this in the env block. Already fixed in v78_fleet scripts.

## What I'd do differently

- **Run a11y on every iter even on tooling-debt arcs**. Catching the SolverInflightTicker WCAG violation took until iter-0 of V78 — it was hiding since V77. If V77's UX scorer hadn't been at "≥17 specs PASS" forgiving threshold, V77 close would have caught it. **Lesson**: V78's UX 100% threshold should have been V77's UX threshold.
- **Charter §6 should bake in "no rebalance during arc"**. If we're going to rebalance Pillar subscores (25→20), do it BEFORE iter-0. Otherwise the iter-0 baseline drops with the rebalance + the new subscore failing = double regression and noisy diagnosis.
- **Document the explicit "Pillar count stays at N" commitment in CLAUDE.md if this pattern continues**. Not project-wide rule (yet) but worth flagging as a discipline.
