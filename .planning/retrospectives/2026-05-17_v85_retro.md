## What worked

1. **V6 interpretation as "bridge to real artifacts" (not "another visual demo") was the right pivot.**
   The 5th verbatim re-issue created interpretation pressure: V6 could have been (a) another curated visual layer parallel to V4/V5, OR (b) something orthogonal. V83/V84 close DECs explicitly forewarned: V6 should pivot strategically (bridge to real solver) rather than inflate the curated showcase. V85.1 charter §1 honored that. **Lesson**: when consecutive identical mandates produce diminishing curated substrate (V4 + V5 already cover demo layer comprehensively), the next pivot should be orthogonal — typically toward closing the biggest structural carry. Real-data bridge closes the 5-arc live-solver-hookup carry without crossing the V130/V132 security boundary.

2. **READ-ONLY framing eliminated security-boundary risk entirely.**
   V6 bridge consumes existing GET endpoints. Zero new MUTATING_ROUTES. Zero new auth surface. Codex review wasn't needed (v2.2 1-sync-trigger not hit). **Lesson**: when a bridge feature CAN be designed as read-only-against-existing-endpoints, do that first; defer write/trigger semantics to a dedicated arc (V86 candidate). Security-boundary changes deserve their own review-heavy arc, not a piggyback on a substrate-grow arc.

3. **The committed FAILED run for lid_driven_cavity (`solver_diverged`) is a GIFT for the bridge.**
   The only committed real artifact for any case is a failed solver run. Initial reaction: "lid_driven_cavity should have a successful run for the bridge demo". Better reaction: "lean into the failure". V6.A surfaces it as "Postprocess · FAIL · solver_diverged"; V6.C diff panel flags it as `verdict_mismatch` divergence against the curated PASS narrative. The bridge is more credible BECAUSE it surfaces real failures honestly. **Lesson**: when real-world demo data has imperfections (failures · placeholder Re=99999999 · empty key_quantities), surface them; don't sanitize. The divergence between curated narrative and real artifact IS the value of V6.C.

4. **Denylist-checked V130 invariant across 4 test files locked the AI passive-observe stance.**
   V85.2 reader · V85.3 sandbox · V85.4 diff panel · V85.5 truth-gate — each has explicit denylist assertions ("click here" / "auto-fix" / "execute" / "remediate" / "fix it") to prevent any V130 erosion during future edits. **Lesson**: when a feature touches AI-advisor-vs-driver tension, lexical denylists are cheap permanent guards. They catch slip-ups that semantic review would miss.

5. **iter-0 = 100/100 immediately on a strategic-pivot arc (V83 pattern reproduced).**
   V82 + V83 both hit iter-0 = 100. V84 had iter-0 = 86 (baseline 83 async-mount drift). V85 returned to iter-0 = 100 because V85 substrate is steady-state (BridgeModeShowcase + LiveVsCuratedDiffV6 don't involve post-click async mounts). **Lesson**: V84.6 baseline async-mount risk class is real but narrow. Steady-state baselines (which V85 produced) don't carry this risk. When designing new visual surfaces, prefer steady-state (URL + props determine render) over post-click async (which can drift across scorer-vs-manual contexts).

## What surprised us

1. **The bridge data layer was simpler than expected because backend already had `/run-history/{run_id}`.**
   Charter §2 anticipated V85.2 might need to add a new GET endpoint. Surface scan during V85.2 found `ui/backend/routes/run_history.py` already serves `RunDetail` with everything V6.A needs (case_id · run_id · success · exit_code · verdict_summary · failure_category · task_spec · key_quantities · residuals). V85.2 became a pure data-mapping module with zero backend changes. **Lesson**: surface-scan discipline (per DEC-V61-088) prevents accidental endpoint duplication. The Pre-implementation grep saved a sub-DEC of effort.

2. **The diff panel's V130 denylist test caught a phrase I almost wrote.**
   Initial divergence note for `verdict_mismatch` said "Real run failed — click to remediate". The denylist test (asserting no "click" / "remediate" in observation text) forced a rewrite to "Real run did not pass; curated narrative shows the expected-pass path." Better wording AND V130-compliant. **Lesson**: V130 denylist tests aren't just regression guards — they actively improve the prose. The constraint forces descriptive language over imperative.

3. **The blueprint document at 179 lines mirrored V5's 177 lines almost exactly.**
   Without trying, V85.1 blueprint landed at 179 lines, V83.1 V5 blueprint at 177 lines. **Lesson**: a well-scoped blueprint doc converges to ~180 lines (north star + contracts table + 4 contract specs + reverse-stops + 4Q gate + honest disclosures + substrate map + test substrate). Above 220 = bloat; below 130 = thin. 180 ± 20 is the natural size.

4. **Pure data module + prop-passing made V6 trivially testable.**
   V85.2 V6.A reader is a pure function — `getBridgeStepState(artifact, step) → BridgeStepState | null`. No React, no fetch, no router. 17 contract tests run in 1 second. V85.3 V6.B sandbox takes the artifact via prop (parent does the fetch). This decoupling means: (a) data layer fully testable without DOM, (b) UI layer testable with mock artifacts injected via prop. **Lesson**: separating "fetch the data" from "shape the data" from "render the data" pays off for testability. The fetch lives in `WorkbenchShellV3` (already wired with `useQuery` patterns); V6 doesn't need to invent a new fetch story.

5. **The "graceful degrade" pattern shows up TWICE in V6 (V6.A + V6.B).**
   - V6.A: artifact null → returns null
   - V6.B: bridgeRequested but bridgeArtifact null → falls back to curated `getSandboxStepState`
   - V6.C: artifact null → component renders nothing
   - V6.D: artifact null → showcase renders nothing
   All four contracts have explicit null guards. **Lesson**: bridge-class features should ALWAYS have an explicit "missing artifact → silent curated fallback" path. Never crash; never error-toast; never auto-trigger. The graceful-degrade discipline is what makes the bridge safe to ship without backend artifact guarantees.
