## What worked

1. **"No scoring change" was operationally smaller than feared**.
   V79 charter §4 committed to ZERO scorer changes. The realistic worry: existing scorers might not detect the V79 work as "progress", making the substrate look invisible. In practice, the V78 scorers absorbed the V79 work cleanly — the additional 8 playwright specs (5 Tab walks + 3 SSIM gate) ran through the UX scorer's 100%-pass threshold and just had to pass. The substrate either passes or fails the existing measurement; no new measurement axis is needed for the work to count as progress.

2. **vtk.js camera presets were 50 LOC + 1 kernel method**.
   `setCameraPreset(preset)` on viewport_kernel + 3 buttons in VtkCanvasV3 + bounds-derived camera distance. Compute `computeVisiblePropBounds()` once, pick position based on preset, resetCameraClippingRange + render. The "industrial parity" carry took less than 30 minutes.

3. **SSIM batch mode self-consistency is a real gate**.
   V78.2's `--batch` mode was useless (compared each baseline to itself, trivially returned 1.0). V79.3 upgraded `--batch` to actively reject any baseline whose self-SSIM falls below 0.9999 — catches file-level corruption, partial writes, truncated PNGs. 76 baselines passing this gate is a measurable substrate property.

4. **Tab-walk test is a coarse but useful gate**.
   "≥8 distinct focus stops per step" caught nothing on first run (good — the substrate is already keyboard-navigable). But the test now sits in CI, ready to catch the next scrollable-region-focusable / focus-trap / hidden-region regression. Cheaper than waiting for axe-core to surface it post-merge.

## What surprised us

1. **Baseline 63 drift from a 4-button cluster vs single button** was inevitable.
   V79.1 added 3 sibling buttons (front/top/iso) next to Reset. The V76 baseline snapshotted just the Reset button. The pixel diff has the new buttons visible alongside; not a regression, just a substrate expansion. Re-snap was the right move. **Lesson**: when adding sibling controls to an existing tested element, the baseline always needs re-snap. Add this to V80 charter as a hygiene rule.

2. **External lockfiles blocked install for hours**.
   Discovered another playwright project (`~/Desktop/Jerry Rusty Lake/`) held the install lockfile since 12:17 (4+ hours). Removing the lockfile would risk corrupting that install. Honest move: skip the install, land the config, document. **Lesson**: playwright's cache locking is per-machine not per-project. Multi-project users will hit this. The config-only fallback is a reasonable substrate.

3. **Zero scorer changes worked on first try**.
   V78 was careful to bake the "no rebalance during arc" lesson. V79 went one step further: no scorer changes at all. The iter-0 → iter-1 transition was a single baseline re-snap, not a scorer mutation. **Lesson**: scoring framework discipline can hold across multiple arcs without bespoke threshold management each time.

## What I'd do differently

- **Try to free the playwright lockfile early in the arc**. Could have checked `~/Library/Caches/ms-playwright/__dirlock` at iter-0 and either (a) waited for the held install to finish or (b) flagged the user to release it. V80 charter should put this in pre-flight checks.
- **Add a "this arc adds N scorer changes" line to charter §4** to make the discipline visible. V78 charter §5 said "Pillar count stays at 16" but didn't explicitly say "0 scorer changes". V79 made the commitment more explicit. V80+ should inherit.
- **The V78 scorer overwrite during V79 verification was annoying**. The `v78_fleet/score_all.sh` writes to `V78_iter_N.md` regardless of which arc is running — so calling it during V79 iterations overwrites V78's close evidence. Workaround: backed up + restored, but the architecture is wrong. V80 could either pass an arc-prefix to score_all OR rename to `vN_fleet/score_all.sh <arc_label> <iter>`.
