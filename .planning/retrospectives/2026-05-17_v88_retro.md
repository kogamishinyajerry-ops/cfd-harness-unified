## What surprised us

1. **The naive `bcSetup && configReady` composition silently broke V87.**
   I expected V7's happy path to keep working because the V87 e2e + visual baseline 84 had no V8 wiring · "V8 isn't in those tests so it can't affect them" was my mental model. Wrong: the WorkbenchShellV3 hooks ALWAYS instantiate V8 now (the hook itself runs even when no V8 UI is mounted), and its `configReady=false` flows into the V7.A gate composition. The blast radius of new shell-level state is larger than the blast radius of new UI components. **Lesson**: shell-level state additions (hooks instantiated unconditionally in WorkbenchShellV3) have a wider blast radius than component-level additions. Snapshot the score IMMEDIATELY after shell-level wiring + diff-spot-check whatever regressed.

2. **The 7-solver allowlist is the right initial scope.**
   V8.B includes 7 known OpenFOAM solvers (icoFoam · simpleFoam · pisoFoam · pimpleFoam · interFoam · rhoCentralFoam · buoyantSimpleFoam). I worried this would feel too narrow vs. OpenFOAM's ~50+ shipped solvers. But the cfd_breadth pillar 8 already independently verifies regime coverage (turbulence · compressibility · steadiness · BC types · meshing) · pillar 8 still scored 100. The 7-solver list explicitly covers all major regimes. **Lesson**: scope by regime coverage, not by raw count. 7 carefully-chosen solvers > 50 ambiguously-known ones from a user-error standpoint.

3. **The `parseControlDictFields` regex is fragile but bounded.**
   I wrote a regex that matches `^\s*(field)\s+([^;]+);\s*$` for the 5 known fields. It works on canonical OpenFOAM controlDict shapes but would miss any encoded inside `{ ... }` blocks. For controlDict specifically, all 5 fields ARE at top level in production. But if a future V9+ extends V8 to fvSchemes / fvSolution (which DO use nested `{}` blocks), this regex needs replacement. **Lesson**: documented in serializer doc-comment that it's controlDict-specific. V9+ extension to other dicts will need a real parser.

4. **PostImpl override pattern was required to keep `useSolverConfigStateV8` tests deterministic.**
   The hook calls `api.postRawDict` which uses real `fetch`. To unit-test the hook without a network mock, I added a `postImpl` constructor option (matching V7.B's `fetchImpl` override). Without this, vitest would have had to mock `global.fetch` per test. **Lesson**: constructor-time DI for fetch dependencies is the simplest pattern across the codebase · V7.B, V8.D both use it. Codify it in the v3 blueprint as the standard for testable hooks.

5. **Validator + hook + component layering ended up cleaner than the charter implied.**
   Charter section §2 listed V8.A → V8.B → V8.C → V8.D in alphabetical order. The actual build order (B → D → C → A) is the natural data-flow order. Reading the test files in that order is more comprehensible than reading the contracts in alpha order. **Lesson**: documentation order ≠ build order ≠ reading order. Acknowledge each explicitly in retro to help future arcs.

6. **Iter-2 hit a pre-existing flake on V81.3 baseline #77 that had been stable across V82-V87 closes + V88 iter-0/1.**
   The flaking spec is `comparator-gold-actual-lid_driven_cavity-u_centerline` (visual baseline #77 · introduced in V81.3 · 3 arcs ago). It passed in iter-0 and iter-1 of THIS arc but failed in iter-2 (both first and re-run attempts). The spec has nothing to do with V8 substrate — comparator surface is V81.3 ComparatorV4, not the BottomPanel/SolverConfigEditor work. The hypothesis is chromium-render non-determinism on this specific baseline (the only one with this drift behavior in the run). I made a conscious choice to NOT retry-until-pass: that path would inflate the close to "3-consec like V83/V85/V86/V87" but the data does not support it. The 2-consec close gate is met on iter-0+iter-1 honestly. **Lesson**: when a pre-existing baseline flakes during your arc's close iters but was stable before AND your arc didn't touch the related surface, accept it as flake + document candidly. Retry-until-pass is iteratively dishonest. V89+ can investigate baseline #77 stability as an Open Q if it keeps recurring.

7. **TypeScript Tuple-call inference issue in mock-call assertions.**
   `vi.fn(async () => ResponseShape)` → tsc gave the mock `.mock.calls` an empty-tuple type because the function signature wasn't pinned to the explicit parameter list. Fix: explicit type annotation on the `postImpl` variable. Took 60 seconds once tsc surfaced the error. **Lesson**: vitest mock fns benefit from explicit typing when used in tuple-destructure assertions. Pattern worth codifying.

   `(!v8Hydrated || configReady)` is the second graceful-gate composition (V6 also used similar logic for `bridgeArtifact ?? curated`). Codify in v3 blueprint as: "additive integrations between v3-feature layers MUST use graceful composition · the new layer blocks only when both (a) hydrated/active AND (b) explicitly invalid". **Action item**: add a paragraph to `.planning/blueprints/v3/INDEX.md` or v3 GLOSSARY.
