## Methodology lessons (5 new, applicable to D)

### L1 — "Schema field names are aspirational"

V61-116 R6 caught that `manifest.bc.patches` exists in the v2 schema but no current code path populates it. Required fields can be schema-declared without an actual write path. **For D (LLM integration), trace the write paths of every field the LLM is allowed to set, not just the schema.**

### L2 — "Append-only manifest records lie about current state"

V61-116 R7 caught that `manifest.history` and `overrides.raw_dict_files` never invalidate. setup_bc → re-mesh sequence leaves them claiming "BC done" when BC dicts are now stale. **For D, if the LLM gets read access to manifest history, surface the staleness signal explicitly so it doesn't reason from outdated state.**

### L3 — "Filesystem-mtime checks are robust if the right file is chosen"

V61-116 R8 caught that polyMesh/boundary is touched by both mesh generation AND BC setup, so it's not a clean "mesh time" signal. polyMesh/points is. **For D, when the LLM needs to understand "what state changed when", the answer is to find the files that ONLY one operation writes.**

### L4 — "Long chains converge productively when finding-density stays > 1/round"

V61-116 (11 rounds, 15 findings, 1.36/round) and V61-108-A (11 rounds, similar density) both converged. **For D, don't aim to minimize round count; track findings-per-round. Stalling looks like 2+ consecutive rounds with 0 findings; productive iteration looks like steady density past round 5.**

### L5 — "Engineer-first UI redesign causes responsive-regression sibling defects"

V61-115 R1→R2: fixing a hidden-sidebar regression created a "stranded mobile users" sibling defect. Pattern: when fixing a layout primitive (Layout / TopBar / Sidebar), enumerate ALL routes that consume the primitive. **For D, enumerate ALL frontend consumers of any new operator-endpoint adapter before declaring fix complete.**

## Risk_flag intake template additions

Three new intake risk_flags proposed for RETRO-V61-001 candidate intake:

1. **`state_machine_with_multiple_stores`** — fires when DEC scope includes any service that reads from ≥2 file paths whose update timing is independent (manifest YAML + flat YAML; manifest + filesystem; etc.). Adds ~5-8 rounds expected.

2. **`schema_field_aspirational_check`** — required for any DEC that consumes a schema field as an authoritative signal. Author must trace the write path before treating as canonical. Adds 1 round expected for verification.

3. **`responsive_consumer_audit`** — required for any DEC modifying a Layout / TopBar / Sidebar primitive. Author must enumerate Layout-mounted route consumers. Adds 1 round expected.

These are additive to existing risk_flags (`executable_smoke_test`, `solver_stability_on_novel_geometry` from RETRO-V61-053) — no existing flag changes.

## Open questions

1. **Is there value in "Kogami catches state-machine pitfalls" pre-Codex?** V61-116's 11 rounds caught all the issues in code review but pre-implementation Kogami (currently SKIP for routine code) might have surfaced "you're modeling 4 stores; here are the pitfalls" upfront. Worth experimenting on D? Cost: 1 Kogami call (~5 min subprocess); benefit: maybe shave 3-5 Codex rounds.

2. **Should `findings/round` density be a Codex trigger?** If a chain hits round 8+ with steady density > 1, it's productive iteration. If round 8+ with 0 findings 2 rounds running, it's stalling. Could codify "round-8-density-check" as a self-prompt for the author.

3. **D-specific question (LLM integration · V61-118)**: when the LLM proposes a parameter set, what's the analyzer's role? V61-116 built the rule-based foundation; D wraps it in dialogue (V61-119). But the LLM itself reasons over the analyzer's output — does the analyzer's `notes` field need a "machine-readable" twin (structured JSON vs. human-readable string)? Defer to V61-118 design.
