### Substrate fragility uncovered

- **Surface-scan discipline (DEC-V61-088) prevented gratuitous endpoint duplication.** The user-selected preview for the V86 axis question assumed "new POST /api/cases/{id}/runs route". Surface scan caught the existing `/api/import/{case_id}/solve-stream` BEFORE charter commit. I surfaced the discovery via a focused AskUserQuestion offering 3 dispositions (extend / parallel-new / refactor). User selected (a) extend. **Lesson**: when a user mandate or initial design implies a new backend route, the pre-implementation surface scan ALWAYS pays off · the discovery either confirms the gap (proceed) or surfaces a duplication risk (re-decide). The 2-question gate (mandate interpretation + disposition) added ~1 turn of latency and saved a multi-week mis-pivot. Worth keeping as discipline.
- **`SolveStreamContext.tsx` pattern was the right reference but wrong abstraction shape for v3.** Legacy `step_panel_shell` uses a Context provider · v3 substrate uses hooks throughout (`useQuery`, `useSseResidualStream`, etc.). I copied the SSE-parsing approach but cast it as a hook (`useSolverRunStateV7`). Cleaner separation between state machine + side effects · easier to unit-test (no provider needed). **Lesson**: surface-scan findings are starting points, not final blueprints. Adapt the pattern to the host substrate's idioms.
- **Generation counter (genRef) for stale-run handling came directly from legacy.** When user clicks Run twice quickly, the second click should abort the first run cleanly. The legacy provider used a generation counter (genRef.current++); I kept the same pattern in `useSolverRunStateV7`. Zero contract test failure means the pattern translated cleanly. **Lesson**: race-condition patterns from production code (legacy SolveStreamContext was battle-tested) port well when the new code follows the same lifecycle shape.
- **Mandate-wording shift was the critical signal — surface-scan was the discipline that paid it off.** Had I treated the 22nd mandate as another V83→V85 verbatim re-issue, I would have either (a) interpreted as V6 substantiation (mirror pattern · ignores wording change) or (b) committed to a multi-week backend pivot (the user's selected preview assumed this). Both would have been wrong: (a) wastes the user's wording-shift signal · (b) builds endpoints that already exist. The AskUserQuestion + surface scan together resolved a 2-axis interpretation ambiguity in 2 turns. **Lesson**: when a mandate wording changes, AskUserQuestion is warranted · when the user-selected axis implies new backend work, surface-scan is mandatory.

### Strategic-arc precedent: 4th strategic pivot

V86 (V7 LAND, 4th strategic pivot · live execution) joins V80 (V4 LAND · 1st), V83 (V5 LAND · 2nd), V85 (V6 LAND · 3rd). Each strategic pivot was a deliberate axis change:
- V80: introduced curated demo substrate (V4 static-knowledge)
- V83: extended into interactive demo (V5)
- V85: bridged to read-only real artifacts (V6)
- **V86: extended into write/execution (V7 · USER-triggered live runs)**

The pattern: each strategic pivot extends substrate ONE LAYER OUT from the static center. V80 added narrative layer · V83 added interaction layer · V85 added real-data-read layer · V86 added real-data-write layer (via USER click, not AI). **Lesson**: strategic pivots are best when they extend ONE concentric layer outward · skipping layers (e.g., V83 directly to V7) would have left V6's read-only bridge unbuilt · V6 had to land first so V7's post-run handoff (V7.D) had something to hand off TO.
