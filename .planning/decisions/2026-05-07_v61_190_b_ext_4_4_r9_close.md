## New findings surfaced in R9

### F13 · /solve returns 502 Bad Gateway

`POST /api/import/{case_id}/solve` returned **502 Bad Gateway** 11 times
across naca0012 (6×) and pipe_expansion (5×). Workbench `/api/health`
returns 200 throughout; OpenFOAM container `cfd-openfoam` (35h uptime)
healthy. The 502 is consistent with an upstream-gateway error on the
solver-launch path — likely a transient race between the route handler's
solver-spawn and the container's command-pipeline readiness, or an
OOM/disk-pressure failure mode under repeated runs (R9 spawned an
ephemeral OpenFOAM container `compassionate_neumann` that lingered for
42 min).

R7's curl direct E2E (DEC-V61-184) and R8's persona /solve POST
*both* returned 200 on backward_step, so this is not a deterministic
regression — it's a stress-induced failure mode that surfaces under
prolonged automation. F13 is **not** mitigated in this DEC; deferred to
B-ext-5 for diagnosis.

### F14 · DeepSeek API read timeouts under sustained load

backward_step crashed at step 20 with
`llm_chat_failed: The read operation timed out` after 15.5 min waiting
for a chat completion response. R8 saw no DeepSeek timeouts; R9 added 1
within 31 minutes of total runtime. This is an **external** failure mode
(api.deepseek.com upstream), not workbench. Mitigation options for
B-ext-5: tighter `OpenAICompatClient` per-request timeout + retry on
read-timeout; or model-vendor swap (e.g., gpt-5.4 via Codex relay).

## Recommendation for B-ext-5

**Do not iterate B-ext-4 further.** R7→R8→R9 traversed three distinct
fix surfaces (anti-mesh-cycle, F11, F12) with verdict pass stuck at
0/3. The remaining gap is no longer a single fixable defect.

**Strategy pivot for B-ext-5:**

1. **Diagnose F13 first** (workbench /solve 502 stress mode). Probably
   container resource limits or solver-spawn race. Without /solve
   stability, persona success rate is bounded above by 1/3 (R8's lone
   success was on the cell with simplest physics — backward_step
   channel).

2. **Re-evaluate the 3-cell × 3-persona charter.** naca0012 has been
   pathological across 5 R-iterations (B-ext-2 R5, R6, B-ext-3 R7,
   B-ext-4 R8, R9). The persona consistently consumes all max_steps on
   geometric/mesh discovery without reaching /solve. This is not a
   workbench-fixable problem — it's a charter-cell-selection problem.
   Recommend swapping naca0012 for a simpler airfoil case (e.g., flat
   plate boundary layer or a Couette setup) for B-ext-5.

3. **Consider reducing scope to 1 cell (backward_step) with
   verdict-formation focus.** R8 backward_step proved the workbench
   chain works end-to-end on a real persona drive. The remaining gap
   on that cell is just persona budget / step-policing — a tractable
   B-ext-5.1 sub-DEC.

4. **DeepSeek read-timeout mitigation** (F14) — small client-side
   retry/timeout patch in `OpenAICompatClient`.

5. **Step 6 verdict-formation rehearsal** as a stand-alone test fixture:
   pre-stage a converged case with known measurement.yaml, point a
   persona at it, see if the prompts + /results-summary + submit_verdict
   chain produces a passing verdict in isolation. If yes, the entire
   gap is upstream of /results-summary; if no, the verdict-formation
   prompt itself needs work.
