# DEC-V61-149 · N4.4 Raw-Dict Escape Hatch Contract

## Status

**Accepted 2026-05-07** — V133 sub-DEC slim 6-field. Low-risk per
N4 charter "low | no [Pre-merge Codex]". This sub-DEC ships **zero
new backend code** — the existing `case_dicts` route already
satisfies every clause of the charter §sub-DEC table N4.4 contract.
The deliverable is an explicit contract verification test file +
this DEC documenting the design decision.

## Decision

**Reuse the existing `case_dicts` route as N4.4's "raw-dict escape
hatch" implementation.** The route already provides:

| N4.4 charter clause | Implemented by |
|---|---|
| "per-dict copy-to-clipboard" | Frontend RawDictEditor consumes the existing GET response's `content` field; copy-to-clipboard is pure UX |
| "read-back from disk" | `GET /api/cases/{case_id}/dicts/{path}` returns on-disk content + fresh etag |
| "engineer can edit in their editor and re-import" | Round-trip: GET → external edit → POST with `expected_etag` from the original GET; 409 on intervening overwrite |
| "disk SHA recorded in trail" (Q3 audit) | Manifest already records `source` + `edited_at` per path; `etag` is the SHA |
| Allowlist of editable paths | `case_dicts/allowlist.py` (DEC-V61-102) |

## Why no new backend code

The N4 charter's threat-model row 5 requires:
> "Raw escape hatch loses engineer's edits — N4.4 records SHA of
> disk state at read time; commit checks SHA still matches before
> overwrite; mismatch → 409 conflict"

This is **identical** to the existing `case_dicts` POST behavior
(test `test_post_etag_mismatch_returns_409` in
`test_case_dicts_route.py` already exercised it pre-N4.4).

Adding a parallel "N4.4 escape-hatch" endpoint would create two
overlapping mutators on the same set of dict paths — exactly the
charter §threat-model row 6 "raw vs structured dict-write coexistence
drift" risk that V102's existing allowlist isolates.

## What this sub-DEC adds (small)

- An N4.4-tagged contract verification test file
  (`test_n4_4_escape_hatch_contract.py`) that exercises every clause
  of the contract end-to-end against the existing route surface. If
  a future change breaks one of these behaviors, this file fails —
  providing a stable N4.4 contract guard separate from the
  general-purpose tests in `test_case_dicts_route.py`.
- This DEC documents the design decision so future readers don't
  hunt for an "N4.4 endpoint" that doesn't exist.

## Why N4.4 explicitly does NOT extend the V102 allowlist

The N4.1 BCContract writes `0.orig/U` and `0.orig/p`. These are
intentionally **excluded from the allowlist** (per V102 comment
"0/{U, p, T, k, ...} are intentionally EXCLUDED. Editing those by
hand silently breaks the face_id → patch invariant"). N4.4 does not
change this. Engineers wanting to tweak BC values use the N4.1
structured route, NOT the raw escape hatch.

For dicts the engineer SHOULD be able to raw-edit (`system/controlDict`,
`system/fvSchemes`, `system/fvSolution`, `constant/physicalProperties`,
`constant/momentumTransport`, etc.), the V102 allowlist already
includes them.
