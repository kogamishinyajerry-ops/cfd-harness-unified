# DEC-V61-225 · CHT runner-wire — LIVE run side (P3 W3.2b)

## Context

DEC-V61-224 re-diagnosed the W3.2b blocker: the workbench execution path
(`foam_agent_adapter`) is hardwired to a **nonexistent Foundation OF10** image +
the **ESI-only** solver `chtMultiRegionSimpleFoam`, while the only runnable
backend (`cfdtrust`) uses Foundation **OF11** (`openfoam/openfoam11-paraview510`,
on disk) via `foamRun`. The user chose **Option A: reconcile the adapter to
OF11/foamRun and actually run CHT.**

**A 2026-06-03 probe + live experiment PROVED this path works** (not speculation):

- **Probe**: `foam_agent_adapter.execute()` (`src/foam_agent_adapter.py:563`)
  hard-fails at the docker-connect step (`:581-601`) because container
  `cfd-openfoam` is **absent** — it does NOT mock-fallback. So the *entire*
  TaskSpec→adapter execution path is dead in this env; runnable-coverage=1 (RANS)
  was produced by `cfdtrust`/OF11, **never** by this adapter. This is project-wide
  execution-path staleness, not a CHT-only gap.
- **Live run**: the W3.2a generator's case (`_generate_cht_multi_region`) was run
  in the OF11 image. `blockMesh` ✅ (400 cells) and `splitMeshRegions -cellZones`
  ✅ materialised 3 regions + `region_*_to_region_*` `mappedWall` coupled patches —
  **the risky mesh side (the V90/V92/V94 death-chain territory) is OF11-clean
  as-is.** After a **bounded** set of ESI→Foundation dict translations,
  `foamMultiRun` ran **200 SIMPLE iterations to `End`**, all 3 regions solving
  (`region_solid` e / `region_hot_fluid` & `region_cold_fluid` h+p_rgh+U),
  continuity errors ~4e-8, **ZERO ±1e+300 sentinels (V14 avoided)**, wrote `200/`.
  Full log: `.planning/intel/p3_w32b/of11_foammultirun_solve.log`.

## Proven recipe (the W3.2b contract)

**Mesh — runs AS-IS in OF11 (no change):** `blockMesh` →
`splitMeshRegions -cellZones -overwrite`. `foamMultiRun` derives the per-region
fluid/solid solvers from `constant/regionProperties` (the master controlDict
`application` line is cosmetic to it).

**ESI→Foundation translations (6, all confirmed against the live solver):**

| # | File | ESI (generator emits) | OF11/Foundation (required) |
|---|---|---|---|
| 1 | `constant/region_solid/thermophysicalProperties` | `transport constIso` | `constIsoSolid` |
| 2 | ″ | `thermo hConst` | `eConst` |
| 3 | ″ | `energy sensibleEnthalpy` + `Cp` | `sensibleInternalEnergy` + `Cv` |
| 4 | `constant/<fluid_region>/g` | only top-level `constant/g` | per-region `g` for each fluid |
| 5 | `system/<fluid_region>/fvSolution` SIMPLE | `rhoMin`/`rhoMax` | removed (→ optional `fvConstraints` `limitPressure`) |
| 6 | `system/region_solid/fvSolution` | solver+relax `h` | `e` |

The coupled-baffle BC `compressible::turbulentTemperatureCoupledBaffleMixed`
(0/<region>/T) ran **as-is** in OF11 (no translation needed). Solver = `foamMultiRun`.

## Decision (proposed)

Wire the CHT live-run into the adapter via a **runtime ESI→Foundation
translation layer**, targeting the OF11 image, and **remove the W3.2a fail-loud
boundary**. Chosen design: **(b) translate at run time, do NOT re-target the
generator.**

- **Why (b) over (a) re-target-the-generator**: W3.2a's load-bearing property is
  "the generated case round-trips through the REAL W3.0.x extractors" (the
  `region_properties_reader` + `thermo_dict_multi_region` contract, 519 tests).
  Re-targeting the generator to Foundation keywords (`Cv`, `eConst`, `e`) would
  ripple into the extractor contract + those round-trip tests. A runtime
  translation step isolates the OF11 reconciliation to the run path — where it
  belongs — leaving the generator + extractor contract untouched.

## Implementation plan

1. **OF11 image/container wiring** — point the adapter's docker-exec at the OF11
   image. Either (i) start a persistent `cfd-openfoam` container from
   `openfoam/openfoam11-paraview510`, or (ii) parametrise CONTAINER_NAME/image +
   ephemeral `docker run`. Change `source /opt/openfoam10/etc/bashrc` →
   `/opt/openfoam11/etc/bashrc` (`foam_agent_adapter.py:8386`). **Scope decision
   1 below** governs whether this also fixes the RANS path.
2. **CHT dispatch (replace the W3.2a boundary at `:815-831`)** — on
   `CHT_MULTI_REGION`: generate (W3.2a) → apply the 6 translations →
   `blockMesh` → `splitMeshRegions -cellZones -overwrite` → `foamMultiRun` →
   parse residuals/continuity → `ExecutionResult(success=True, is_mock=False)`.
   The translation is a small deterministic post-generation pass (a
   `_translate_cht_esi_to_foundation(case_dir)` helper).
3. **Tests** — `test_cht_execute_hits_explicit_live_run_boundary` (the W3.2a
   boundary assertion) **must flip** to assert a real run (or a structured
   docker-unavailable BLOCK when no OF11 container). Add: a translation unit test
   (6 keyword pins) + an opt-in live-run test gated on a `CFD_LIVE_OF11=1` env
   (so CI without docker stays green) mirroring `cfdtrust`'s
   `CFDTRUST_LIVE_NETWORK_TESTS` pattern.
4. **No regression** — 519 existing tests stay green (generator + extractors
   untouched by design (b)).

## Scope decisions (surfaced — load-bearing, blast radius)

1. **CHT-only vs also reconcile the RANS path.** The OF10→OF11 bashrc change +
   image re-point is in the SHARED docker-exec path; it affects every solver. The
   adapter's RANS path uses ESI `simpleFoam`; OF11 wants `foamRun -solver
   incompressibleFluid`. Options: (1a) **CHT-only** — gate the OF11 path to
   CHT_MULTI_REGION, leave the (already-dead) RANS adapter path as-is; smallest
   slice. (1b) **also reconcile RANS** — repair the whole adapter execution path
   to OF11 (bigger, but it's the honest fix for the project-wide staleness the
   probe found). Recommend **1a for W3.2b** (keep the slice tight; RANS-reconcile
   = its own follow-up sub-DEC), explicitly logging that the RANS adapter path
   stays dead until then.
2. **Persistent container vs ephemeral `docker run`.** `cfdtrust` uses ephemeral
   `docker run --rm`; the adapter assumes a long-lived `cfd-openfoam` container.
   Recommend mirroring `cfdtrust` (ephemeral) to converge the two backends.
