## 1. North star

Bring the workbench's **B-module (mesh)** parity from ~25% to ~60% of an industrial preprocessor's expected control surface, **without** re-introducing AI auto-mutation pathways. Engineer drives the mesh; AI may *suggest* values via read-only `GET` endpoints (V132 contract).

Concretely: an engineer with a non-trivial STL geometry (multi-solid, internal flow + external walls) can **manually** specify sizing strategy + refinement zones + boundary-layer prisms + read fix suggestions for `checkMesh` failures, all from Step 2 UI, and reach a polyMesh that passes `checkMesh` ≤ 1 severe non-orthogonality patch.

## 3. Sub-DEC decomposition

Per DEC-V61-133 §2 scope-driven rule: **N2 charter = full DEC** (cross 3+ modules); **each N2.x = slim 6-field DEC**.

### N2.1 · Sizing field UI + backend lc-per-region
**Scope**: Replace single global `lc` with a sizing-field object the engineer fills:
```yaml
sizing:
  base_lc: 0.05
  min_lc: 0.005
  max_lc: 0.10
  curvature_target_size: 0.02   # gmsh "Mesh.MeshSizeFromCurvature"
  proximity_layers: 4           # gmsh "Mesh.MeshSizeFromBoundary" + ratio
```
**Backend changes**:
- New schema `MeshSizingField` (Pydantic) in `services/meshing_gmsh/`
- `gmsh_runner._configure_sizing_field` reads field, writes gmsh options
- `mesh_imported.py` POST body accepts `sizing_field: MeshSizingField | None` (back-compat: omitted = current behavior)
**Frontend changes**:
- `Step2Mesh.tsx` adds a collapsible "Advanced sizing" panel with 5 inputs + reset-to-mode-default
- Validates min ≤ base ≤ max client-side
**Acceptance**:
- [ ] User can set sizing field manually, `POST /api/import/{case_id}/mesh` with body honors it
- [ ] LDC fixture re-meshes with custom sizing (manual smoke)
- [ ] No new mutating route (POST stays the existing V132-registered endpoint)
- [ ] `test_ai_advisor_contract.py` still passes (no envelope drift)
**Risk class**: medium (gmsh option surface; algorithm well-understood)
**Estimate**: ~150 LOC backend + ~120 LOC frontend + tests

### N2.2 · Region refinement zones
**Scope**: Engineer adds refinement zones via a list of `{geometry: box|sphere|stl, params, level: 1-3}`:
```yaml
refinement_zones:
  - geometry: box
    bbox: [0.0, 0.0, 0.0, 0.5, 0.5, 0.5]
    level: 2
  - geometry: sphere
    center: [0.25, 0.25, 0.25]
    radius: 0.10
    level: 3
```
**Backend changes**:
- `MeshRefinementZone` schema (discriminated union on `geometry`)
- gmsh path: emit `Box` / `Ball` size fields with `LcMin`/`LcMax`
- `mesh_imported.py` POST body accepts `refinement_zones: list[MeshRefinementZone]` (back-compat: empty)
- (optional, deferred) STL-bounded zone — uses gmsh `Distance` field on a secondary triangulated surface
**Frontend changes**:
- `Step2Mesh.tsx` adds repeater-list section with add / remove / per-zone form
- Visual hint: bbox is rendered into the viewport (uses existing wireframe overlay infrastructure)
**Acceptance**:
- [ ] User can add ≥1 box and ≥1 sphere zone, mesh respects level (cell-size delta verifiable in `checkMesh -allTopology` output)
- [ ] Zero zones = behavior identical to N2.1
- [ ] LDC fixture refined-near-corner case passes a regression smoke
**Risk class**: medium (geometry validation can edge-case; bbox out-of-domain rejection)
**Estimate**: ~200 LOC backend + ~180 LOC frontend + tests
**STL-volume zones**: deferred to N2.2-followup (spec-only) — full snappyHexMesh `refinementSurfaces` integration is N2.3 territory.

### N2.3 · Prism layer (snappyHexMesh addLayers integration)
**Scope**: First snappyHexMesh integration in this project. Engineer chooses prism strategy on a per-patch basis:
```yaml
prism_layers:
  patches:
    - patch: walls
      first_cell_height: 1.0e-4
      expansion_ratio: 1.2
      num_layers: 5
    - patch: airfoil
      first_cell_height: 5.0e-5
      expansion_ratio: 1.15
      num_layers: 8
```
**Backend changes**:
- Replace `snappyHexMeshDict.stub` writer with full-stack `snappyHexMeshDict` renderer in `case_scaffold/`
- New service `services/meshing_snappy/` (parallel to `meshing_gmsh/`):
  - `snappy_runner.py` — runs snappyHexMesh in cfd-openfoam container (mirrors `to_foam.py` docker-bind pattern)
  - `addlayers_renderer.py` — produces `addLayersControls` block
- New POST endpoint `/api/import/{case_id}/mesh/prism-layers` — **NEW MUTATING ROUTE** → must be added to V132 `MUTATING_ROUTES` registry + behavioral contract test
- Pipeline flow: gmsh → polyMesh → snappyHexMesh addLayers stage → final polyMesh
**Frontend changes**:
- `Step2Mesh.tsx` adds "Boundary layers" section with patch-list (auto-populated from imported case patches) + per-patch form
- Step 2 navigation gains an explicit "Add prism layers" button (separate from "Generate mesh") so prisms are an additive step the engineer chooses
**Acceptance**:
- [ ] User adds prism config on `walls` patch, snappyHexMesh adds layers, `checkMesh` sees y+ field within target bounds
- [ ] LDC fixture: no prisms = same as N2.2 result; with prisms = additional cell layer near walls
- [ ] V132 registry updated, contract test green
- [ ] Pipeline failure modes (snappyHexMesh exit code, layer-add did not converge) mapped to structured `failing_check`
**Risk class**: **high** (new container exec path, new registry entry, snappyHexMesh notoriously fragile on near-degenerate geometry)
**Estimate**: ~300 LOC backend + ~200 LOC frontend + tests; **Codex review pre-merge** likely (security-boundary new POST endpoint touches V132 contract)

### N2.4 · checkMesh advisory recommendations
**Scope**: Per V130 Principle B (AI advises, engineer applies), turn `checkMesh` failures into human-readable fix suggestions. NO auto-apply. UI shows a "Suggested fixes" list under each failed metric; engineer reads and decides.
**Backend changes**:
- New `services/mesh_quality/advisor.py`:
  - Maps `checkMesh` failure codes (severeNonOrtho > 70 / maxSkewness > 4 / maxAspectRatio > 1000) to keyed advice templates
  - Returns `list[FixSuggestion]` with `{metric, severity, suggestion_text, recommended_change: dict | None}`
  - **Critical**: `recommended_change` is metadata only — no apply path
- Extend `GET /api/cases/{case_id}/mesh-quality` (existing read-only) with `suggestions: list[FixSuggestion]`
**Frontend changes**:
- `MeshQualityCard.tsx` adds an expandable "Suggested fixes" panel under each red-zone gauge
- Each suggestion shows the recommended change as a *display-only* pre-filled value the engineer can copy-paste into N2.1-N2.3 forms
**Acceptance**:
- [ ] LDC fixture with deliberately-bad mesh (large lc, no prisms) shows ≥3 suggestions
- [ ] Suggestions reference specific N2.1-N2.3 controls (e.g., "Reduce min_lc to 0.002 in N2.1 sizing field")
- [ ] No new mutating route; `is_mutating_route` returns False for the new endpoint variant
- [ ] V132 contract test green (read-only addition)
**Risk class**: low (advisory layer, no algorithm change, no new mutator)
**Estimate**: ~120 LOC backend + ~100 LOC frontend + tests

## 4. Sequencing & dependencies

```
N2.1 sizing field
  ↓
N2.2 region refinement   (uses N2.1 sizing field for LcMin/LcMax baseline)
  ↓
N2.3 prism layers         (snappyHexMesh introduction; depends on patch detection from M5.0)
  ↓
N2.4 checkMesh advisor    (references N2.1-N2.3 controls in suggestions)
```

**Why strict serial**:
- N2.2 reuses N2.1's `MeshSizingField` schema as its sizing baseline (ref-by-id)
- N2.3 introduces a **new mutating endpoint**, which means a V132-registry update + behavioral contract migration; doing this before N2.1/N2.2 land would force two registry migrations
- N2.4 references all three preceding controls in its advice templates; building it first means rewriting advice when N2.1-N2.3 land

**No calendar gating** (per `feedback_no_schedule_gating.md`). Each sub-DEC closes when its acceptance list is green; next sub-DEC opens.

## 5. Workbench-first acceptance gate (V130 Principle B)

For every sub-DEC, the following **MUST** hold before Status=Accepted:

1. **LLM-offline reachability**: with `LLM_PROVIDER=disabled` env, the engineer can complete the full mesh control flow via Step 2 UI manual inputs. No LLM call required.
2. **AI advisor surface**: any AI helper added is `GET`-only (per V132 `MUTATING_ROUTES` registry). Engineer applies recommendations by clicking the existing manual control.
3. **No envelope re-mutation**: `test_ai_advisor_contract.py` Layer-A passes; new tool dispatch (if any) is Layer-A registered.
4. **Verbatim defense**: if a fix-suggestion (N2.4) produces structured recommendation, frontend renders it as **copy-able text**, NOT as a "Apply" button.
