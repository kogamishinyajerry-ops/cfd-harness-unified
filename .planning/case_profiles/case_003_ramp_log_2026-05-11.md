## Substrate-listening findings (4 new, 1 V-series reclassification)

### F-NEW-1 · A1 mechanical extraction validated on second non-APU industrial case

### F-NEW-2 · FreeCAD subprocess bridge has positional-arg friction
`freecadcmd` auto-opens any positional argument as "file to open", which
clashes with passing script paths/IO paths via argv. Workaround: sidecar
args file (`_probe_args.txt`) at a known path. Works but is fragile. If
this bridge pattern persists across future sessions, consider a proper
subprocess wrapper service in `geometry_ingest/` (next-spike candidate).

When STEP contains both the airframe AND its CFD domain boundaries
(inlet/outlet/farfield), the bbox max extent reflects the **domain**, not
the geometry of interest. Result: P0 flags UNKNOWN even when airframe
bodies themselves are at sensible mm-scale.

- `symmetry_plane`: 2438 m × 0.152 m × 1541 m

**Spike candidate**: extend P0 to accept a `body_class_filter` callback or
take a list of "airframe bodies vs domain bodies". Or downstream caller

## Substrate-listening findings (6 new)

### F-NEW-9 · 50 MB STL cap blocks Q3-deflection airframe (P1 blocker)
`MAX_STL_BYTES = 50 MB` (route line 34) was spec-D for hand-authored STL
uploads. With FreeCAD Q3 tessellation (STAR-CCM+ production default)
the case_003 91-m airframe alone produces an 87 MB ASCII STL.

**Options** (no decision yet, substrate-first):
- (a) Raise cap to e.g. 200 MB for industrial substrate (+ rate-limit at
  proxy if abuse concern) — simplest, but masks the broader "should we
  store binary STL?" question
- (b) Bridge emits binary STL by default (3× smaller per facet) — but
  loses the multi-solid named-block round-trip that detect_patches needs
- (c) Bridge emits ASCII for label-bearing bodies + binary for label-less
  bodies + raises cap to 200 MB; combined output stays ASCII
- (d) Lower Q3 → Q2 (0.1 mm linear) only for airframe-class bodies →
  facet count drops ~4×, file ~22 MB — but loses production-grade
  surface fidelity for the very body that needs it

**Recommendation** (substrate evidence basis): raise cap to 200 MB +
keep ASCII (option a). Real industrial CAD at production tessellation
will routinely cross 50 MB; the cap was authored before APU bay / CRM
substrate experience. The named-block round-trip is load-bearing
(probe C proves it works) so binary STL is a regression.

### F-NEW-10 · Bridge needs a "combined multi-solid" emit mode

## Session 3 follow-up #3 · F-NEW-12 body-class filter landed

**Spike**: extended `detect_unit()` in `unit_detector.py` with a new
optional `body_extents_raw: list[float] | None` parameter. When supplied,
bodies whose max-extent is implausible under every common unit
(mm/cm/m/inch) are discarded as "CFD-domain class"; the largest extent
among the survivors replaces the overall `bbox_max_extent_raw` for the
decision.

**Backward compat**: callers that don't pass `body_extents_raw` get
identical behavior to before. 22/22 existing + new tests green.

### F-NEW-17 (NEW) · Body-class filter accidentally surfaces F-NEW-4
The 100 m industrial upper bound flags the Codex-scaled airframe as
domain-class. This is **substrate cross-talk**: a heuristic designed to
separate airframe from CFD-domain also separates "real-size airframe"
from "implausibly-scaled airframe". It's not a bug — it's a side
benefit. The filter degrades gracefully (3 defects suffice for unit
decision); but in a future case where ALL bodies are above range
(e.g., a ship deck 200 m × 200 m × 30 m), this filter would mis-fire.

Mitigation when needed: make the industrial range configurable per
case (M3 boundary-conditions phase or workbench case-settings panel).
Not needed for case_003.

### Why this matters for the workbench UX

The pre-fix path made the workbench `unit_guess='unknown'` warning
fire on every industrial multi-class STEP — engineers were told to
"set the unit explicitly" even when the STEP header was unambiguous.
Post-fix, the workbench can show `unit_guess='mm'` with confidence
1.0 + a clean evidence trail. The route layer doesn't even need a
change: the route calls `detect_unit` only with overall bbox today;
the bridge OR the route can pass `body_extents_raw` to get the
filtered decision. That wiring is the **next** step (out of this
spike's scope).

### F-NEW-18 · `_guess_units` legacy heuristic preserved as fallback by design

Not a finding to fix; **documents the wiring design**. This is the
substrate-listening price for replacing a deterministic band with an
advisory engine: you add a conservatism guard for the ambiguous
single-class regime so existing flows don't regress.

### F-NEW-22 (NEW) · classifySurfaces is the case_003 upstream wall

End-to-end validation on case_003 surfaced an **upstream wall** that
F-NEW-19's fix cannot reach. Probing the gmsh pipeline stage-by-stage
on `combined_session_4.stl` (82.6 MB, 393,498 facets, 10 named

```
[0.0s] python start
[0.0s] STL = 82.6 MB
[0.1s] gmsh import done
[0.1s] gmsh init done
[0.1s] SIGALRM re-armed for merge stage
[1.0s] gmsh.merge done
... never returns from classifySurfaces (>60s SIGALRM didn't fire,
    >4 min of background CPU before manual termination)
```

`gmsh.model.mesh.classifySurfaces(angle=40°, ...)` groups triangles
into parametric surfaces by dihedral-angle thresholds. On 393k
triangles at Q3 STAR-CCM+ deflection it appears to run super-linear
(empirically minutes-to-hours, not seconds). SIGALRM doesn't deliver
during the call — gmsh's C++ inner loops don't yield to the Python
signal handler. The session-4 M6 probe's 7-minute hang **was
classifySurfaces, not characteristic-length sizing**.

**Implication for F-NEW-19**:
- F-NEW-19 fix is correct: it would help any multi-class load that
  reaches the lc-decision stage (e.g. a simpler airframe + closed-box
  CFD domain at coarser tessellation).
- F-NEW-19 fix does NOT unblock case_003 because classifySurfaces is
  upstream of the lc-decision site.
- F-NEW-22 is independent of F-NEW-19; both must be addressed for
  case_003 to mesh.

**Mitigation options for F-NEW-22** (substrate-first, no decision yet):
- (a) Re-tessellate at coarser Q1/Q2 deflection on bridge upload —
  Q1 (~0.5mm) would shrink 393k → ~10k facets, but loses surface
  fidelity downstream.
- (b) Skip `classifySurfaces` entirely — use the STL's existing solid
  blocks as physical groups directly (gmsh.merge already
  reads named solids per the bridge's combined emit). This requires
  a different gmsh path that doesn't require parametric-surface
  reclassification. Possibly the right architectural move for
  industrial CAD.
- (c) `classifySurfaces(angle=180.0, ...)` — wide angle would merge
  fewer parametric surfaces, faster. But might destroy patch
  separation by collapsing inlet/walls/outlet into one parametric
  surface.
- (d) Set `Mesh.MeshSizeFromCurvature = 0` and other classify-
  related options to disable some inner work. Unclear if classify
  itself accepts a fast-path option.

Likely best mitigation = (b) — there's already a sibling path
(snappyHexMesh) that consumes STL solids directly without
`classifySurfaces` reclassification. The workbench could route
multi-named-solid STL to a "passthrough" gmsh path that uses the
existing solid groupings, OR partially shift industrial-case workflow

### F-NEW-24 (REVISED) · artifact of gmsh tolerance, not substrate

What session 6 labeled F-NEW-24 (9356 degenerate triangles) is **not a
substrate issue**. It's an interaction between gmsh's default
`Geometry.Tolerance=1e-8` and case_003's industrial-CAD scale
(2.4 km bbox × 50μm Q3 features). The combined STL is byte-clean.

**Mitigation** (single-line gmsh option, not a bridge change):
```python
gmsh.option.setNumber("Geometry.Tolerance", 1e-12)
```

Set this before `gmsh.merge()` whenever the workbench is processing
industrial-scale multi-named-solid STL. Inferred guideline:
`tolerance = min(1e-12, bbox_max * 1e-10)` so the absolute tolerance
stays orders of magnitude below the smallest meaningful CAD feature.

F2 path implementation (F-NEW-22 mitigation) must include this
`Geometry.Tolerance` set or the F-NEW-24 symptom returns.

### F-NEW-25 (CONFIRMED REAL) · multi-instance bridge stitching

Two distinct PLC errors from HXT, at different (x,z) coordinates but
sharing y=838200 mm. ~111k facets (28% of input) fail constrained
recovery → many farfield-body shared edges are mis-stitched.

Root cause hypothesis: `step_to_per_body_stl` runs FreeCAD
`MeshPart.meshFromShape` **per body independently**. The 8 farfield-
class bodies (root mount pad, cover, plate, inlet, outlet, symmetry,
farfield top/bottom/outer) are box faces — adjacent boxes share an
edge but their independent tessellations don't enforce vertex
identity at the shared edge. The two ends of a shared edge end up
at slightly different node coordinates in the two box meshes,
creating micro-overlaps when bodies are concatenated.

Bridge fix options (sub-DEC class):
- (a) **Pre-tessellation farfield-merge**: in the FreeCAD sidecar,
  detect bodies whose faces share edges (or are tagged farfield)
  and join them into a single solid before MeshPart.meshFromShape.
  Cleanest; ~100 LOC change to sidecar.
- (b) **Post-tessellation vertex-snap**: in `combine_per_body_stls`,
  parse triangle vertices, build spatial index, snap coordinates
  within tolerance to canonical positions at shared edges. More
  invasive (parse + emit Q3 STL); ~150-200 LOC.
- (c) **Skip combine entirely**: workbench accepts a list of
  per-body STL paths and the gmsh runner does the multi-merge
  internally (each gmsh.merge call respects gmsh.Geometry.Tolerance).
  Requires API change downstream of bridge.

Recommended: (a). Cleanest separation, retains the existing
combine_per_body_stls contract, fixes case_003 at the right layer.
